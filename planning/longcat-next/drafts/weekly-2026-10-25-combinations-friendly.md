# vLLM-Omni 如何应对“卡 × 模型 × 输入”的组合

2026-10-25 调查记录，2026-10-26 整理为阅读版。调查基线为 main `dca119877b`。本次完成了源码核对和隔离 CPU 验证，改进方案尚未实施。

## 为什么这个问题值得解决

部署一个模型时，仅知道“支持 NVIDIA GPU”还不够。还要知道使用哪种卡、需要几张、生成多大的图片、是否同时处理多个请求，以及开启哪些加速功能。

这些选择会相互影响。例如，同一个模型可能在单卡小图上正常运行，在多卡大图、缓存和并发同时开启时暴露问题。所谓“乘法组合”，就是这些选择交叉后产生的大量使用场景。它不是一个要求把所有参数数值直接相乘的公式。

本次调查希望回答两个问题：框架现在在哪里检查这些组合？能否找到一个具体问题，作为改进的起点？

## 当前框架怎样处理一次请求

可以把处理过程理解成四个决定：

1. **选硬件实现。** 检测当前机器的 GPU 或 NPU，选择适合的工作进程和计算算子。有些算子还要求特定卡型、软件版本或张量形状。
2. **选模型流程。** 模型注册表决定要执行哪些阶段，例如“理解输入 → 生成语音码 → 解码成声音”。阶段是处理步骤，可以共享一张卡。
3. **合并部署设置。** 合并默认配置、平台覆盖、并行策略和命令行参数，得到最终的卡布局与开关。这里已有部分卡数和冲突检查。
4. **检查并处理输入。** 检查图片数量、输入格式等，再按请求编号把数据送到对应阶段。更具体的形状或生成状态限制，由模型和运行时继续检查。

这套分工已经能处理很多场景。问题在于，组合规则和验证证据散落在不同层：模型表上的一个“支持”勾选，无法说明某个具体部署组合是否已经跑过。

一个现成例子是 Qwen2.5-Omni：CUDA 默认的三个阶段使用卡 `0、1、0`，NPU 配置则使用 `0、1、2`。前者有两个阶段共享卡，后者使用三张卡。由此可见，“三个阶段”不等于“三张独占卡”。这是部署文件的设置，不是本次新做的性能实验。

## 找到的具体问题：同两张卡被算了两次

TP 是“张量并行”：把一部分模型计算拆到多张卡。VAE 是将生成表示解码成图片的模块。

本次检查的 FLUX.2 测试配置同时设置 `TP=2` 和 `VAE patch=2`。这里的 VAE 解码复用模型计算已有的两张卡；测试辅助函数却把两个度数相乘，要求 4 张卡。

![TP 与 VAE 复用同两张卡，测试估算却再次相乘](figures/shared-ranks.png)

图中的 2 与 4 来自生产配置和测试辅助函数的隔离 CPU 调用。VAE 的源码与文档也说明它复用已有工作进程。这证明计数不一致；还没有验证实际 GPU 分工或队列成本。

| 本次实际检查 | 结果 | 能回答什么 |
| --- | --- | --- |
| 现有 FLUX.2 的 TP2 + VAE2 用例 | 测试函数要求 4 卡，生产配置得到 2 个 worker | 两处资源计算不一致 |
| TP2 + 扩散 CFG2 | 生产配置得到 4 个 worker | 有些并行度确实需要相乘，不能全部改成取最大值 |
| 序列并行 2 + HSDP 权重分片 2 | 配置接受，仍为 2 个 worker | 权重分片可以覆盖已有进程，不必再乘一次 |
| TP2 + HSDP，或 Ring2 + AllGather2 | 配置明确拒绝 | 部分组合限制已存在，应复用现有检查 |

表中后两行只验证配置关系，没有证明这些设置适用于任意模型。源码入口和复现命令保留在[技术原稿](weekly-2026-10-25-combinations.md)与[复现脚本](combinations_probe.py)。

## 还发现了什么

有些加速设置无法应用时，程序会写一条警告，然后继续运行。例如序列并行没有找到模型的切分方案，或编译失败后继续使用普通执行。这种回退可以有合理用途，但用户需要知道实际用了什么。否则“开了加速”与“加速已经生效”容易混为一谈。

测试也会主动减少组合数量：在线测试默认只跑基础组，额外加速组更多放在离线测试；部分测试使用小型随机权重，以降低启动成本。小模型适合检查流程、形状和通信，不能回答真实模型生成质量是否保持不变。

当前通用扩散参数表包含 16 个模型、51 个离线模型/加速配置组；在线默认为 16 个基础组。这些是配置表数量，不是全仓库模型数，也不是已经通过的测试数。

## 建议怎样改

第一步先统一资源计算。测试继续使用现有的加速配置映射，但把“到底创建多少工作进程”交给生产配置推导，并另行检查 VAE 等模块需要的进程组。这样可以修正已确认的重复计数。共享卡上的显存是否足够，仍需独立检查。

第二步让限制在合适的时间被检查。启动前检查卡布局和配置冲突；工作进程初始化时检查真实硬件、软件包与算子；请求到达时检查图像形状、输入数量和生成预算。错误信息应说明哪个设置冲突、来自哪里，而不只给一个深层异常。

第三步记录实际生效状态，并据此选择测试。每项能力都应能回答“用户请求了什么、最后用了什么、为什么回退、在哪个版本与场景验证过”。普通开关可以挑选代表性的交互测试；并发、取消、请求配对等依赖多个条件的问题，仍需要专门用例。

## 与 LongCat CFG 草稿的关系

两份材料都在处理“单个功能正常，组合后怎样仍然正确”的问题。LongCat 的例子是：一个生图请求内部拆成两路计算，必须保持配对与同步；卡数足够、两路落在同一个副本，都不能单独保证同步推进。

这一问题的原理、实际观察和解决思路见 [CFG 生命周期阅读版](cfg-lifecycle-friendly.md)。它与扩散模型的 CFG 卡间并行有关联，但对应的运行时机制不同。
