# LongCat-Next CFG：为什么两路请求必须一起推进

个人 fork 的设计阅读版，尚未实现。问题来自 2026-10-25 的两个隔离 CPU 复现，代码基线为 `longcat-next/code` 的 `53785219b`，依赖模型适配 #5299 `c90ebc1d07ba`。

## CFG 在这里做什么

生成图片时，模型可以同时计算“有提示词条件”和“去掉条件”的两路预测，再用它们的差来增强提示词的作用。这个方法称为 CFG，即无分类器引导。

如果无条件预测记为 `u`，有条件预测记为 `c`，引导强度为 `s`，组合结果是：

`u + s × (c − u)`

公式很短，运行时要求却很严格：两路预测必须对应同一个生成步骤。LongCat 将两路计算表示为两个内部请求，客户端仍只提交一个生图请求。后文称它们为“有条件请求”和“伴随请求”。

LongCat 在每个图像位置逐级生成 8 个离散码。两路需要共享每一级采样结果，再把同一组码反馈给各自的下一步计算。否则它们会逐渐拥有不同的生成历史。

## 当前发现的问题

调度器决定每一轮哪些请求可以使用计算资源。当前模型代码主要根据本轮批次中出现的伴随请求编号判断配对；如果只调度了有条件请求，代码可能按普通请求继续生成。

KV cache 是主干保存的历史计算结果。模型还保存图像码和生成位置等状态。两路提示条件本来就不同，不要求 KV 数值相同；需要对齐的是生成位置与共同采样的码。因此，把“第几步”的数字改成一致，不能补回漏算的步骤或修复错位的反馈。

复现直接调用生产模型方法，但用替身代替了真实深度网络、TP 通信和部分运行时依赖。它确认了这些局部分支的行为，没有证明真实 GPU 调度在某种负载下多常触发，也没有测量图片质量损失。

## 建议怎样解决

把两个内部请求作为一对，贯穿它们的完整处理过程：

1. **创建时记清身份。** 为这一对设置共同编号，并标记谁有条件、谁无条件。后续传输不再只靠字符串后缀临时猜配对。无需展开两路的请求保持单流。
2. **资源一起满足。** 同时检查两个请求的位置名额、每轮计算预算和历史缓存空间。这里的“原子准入”就是要么整对接纳，要么整对等待或失败。
3. **同一步共同推进。** 只有双方都准备好同一生成步骤时，才组合预测、采样并共享反馈。两路原始提示长度可以不同；对齐的是生成进度，不是绝对 token 位置。
4. **一起结束并清理。** 正常结束、达到长度上限、取消、超时或出错，都必须让这一对进入一致终态，并释放缓存、模型状态和请求编号记录。

错误应传回对应请求，避免让一个配对错误无意中停止整个服务。等待还需要期限：永远无法凑齐或无法装入资源的请求，不能无限留在队列里。

## 为什么不能直接换一个调度器

仓库已有 `OmniCFGARScheduler`，Breeze-TTS 使用它。本方案应优先复用这项能力。但它当前要求同步调度、完整处理提示词、关闭 prefix cache 等限制，并对缓存组有要求；LongCat 不能只添加一个类名就接通。

最明显的配置冲突是：LongCat 最大上下文为 65536 token，每轮批处理预算为 8192 token；现有调度器要求后者至少为前者两倍，即 131072。直接接入会启动失败。缩短最大上下文只能绕过这项检查，不能证明调度正确。

改进需要根据每一对请求的真实提示长度和生成上限计算缓存预算，同时明确哪些配置支持。较长的提示词能否分块处理，应作为另一项能力验证。现有单元测试替换了底层调度方法，也不足以证明真实缓存分配行为。

另一个容易遗漏的地方是结束路径：显式取消会经过 `finish_requests`，正常输出后的结束还会经过 `update_from_output → _free_request`。只修改前者，不能保证正常结束或长度到顶时也整对清理。

## 怎样知道方案已经完成

先在真实 CPU 运行时检查多对请求、普通请求混合、缓存压力和各种结束方式，确认不会单独推进或残留状态。再在 GPU 上检查真实计算和通信；最后使用 LongCat 权重，与相同权重的官方参考比较逐级预测、生成码和最终图片。

性能测试需在质量一致时比较有效请求吞吐、尾延迟和显存。例如 P95 延迟表示 95% 的请求延迟不超过的值；“程序输出了图片”不能代替质量或性能验收。

当前本地完整测试曾在导入 `ALLOWED_LAYER_TYPES` 时失败，尚未进入测试；没有完成 GPU、真实权重或 TP 验证。因此当前成果是问题复现与工程设计，不能描述为已经完成 CFG 并发支持。
