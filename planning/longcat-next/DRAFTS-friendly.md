# 投稿草稿：每份材料希望审核者决定什么

这里解释 [DRAFTS.md](DRAFTS.md) 中四份英文草稿的用途和证据。原稿保留可供后续投稿改写的英文正文；目前没有发送或发布。

## 给模型适配作者的说明

这封简短说明希望确认：作者是否愿意将两项小修复吸收到 #5299。它应该直接说明修复了什么、基线是什么、局部测试结果及限制，再附提交链接。

两个修复分别是视觉码与反馈正确性、只读码表共享存储。当前证据来自隔离 CPU 测试，不覆盖真实 GPU、TP 通信或媒体质量。问作者是否希望接收提交，比重新贴一整套模型适配更容易处理。

## 视觉修复 PR

这份草稿的主问题是“保存与反馈给下一步的视觉码是否合法”。它解释两个触发条件：高层额外类被采样，或合法 code 0 的帧被反馈成文字向量。

修改后，每级都排除额外类，保留帧按视觉向量反馈。原基线的 6 项视觉问题用例失败；修改后 12 项新增视觉用例与 56 项已有用例通过。

这些数字来自隔离 CPU 环境。不能把额外类描述为必然数组越界，也不能说这项 PR 解决了 CFG 配对调度。模型前置 #5299 仍是其依赖。

## 存储共享 PR

这份草稿只回答“两个只读消费者是否需要各存一张码表”。已有缓存码表被深度网络再次复制，造成多余常驻存储；共享只读数据可以删除这份复制。

4 项存储回归在原基线失败、修改后通过，核对查值、FP32/BF16、冻结权重、共享指针和重复访问。已有视觉/talker 用例仍通过。

在两表均初始化、BF16 和向量维度 3072 时，重复表合计 882 MiB/rank。它是条件化字节计算，不是端到端显存或吞吐结果；真实权重加载、设备移动和多卡通信仍需检查。

## CFG 设计 issue

这份草稿讨论更大的运行时问题：有条件和无条件两个内部请求，怎样从创建到结束始终保持同一步生成。

旧草稿主要基于源码分支判断。后续隔离调用补充了实际观察：一方可能单独前进；两方处于第 9 步和第 2 步时仍被组合。真实 GPU 调度在什么负载下触发还没有验证。

仓库已有被 Breeze-TTS 使用的通用 CFG 调度器，方案应优先讨论如何复用和补齐它。旧 RFC 中“支持分块 prefill”的目标不能理解成已经实现，甚至也不能直接接入 LongCat；其预算和缓存条件需要单独验收。最新细节见[CFG 阅读版](https://github.com/Cheongroach/vllm-omni/blob/longcat-next/draft-cfg-lifecycle/planning/longcat-next/drafts/cfg-lifecycle-friendly.md)。

因此，正式发布前应更新英文 RFC，提出一个具体职责问题，并保留真实复现边界。等待、明确拒绝或允许回退，是要决定的行为，不应无声地改变生成语义。

## 怎样使用这些草稿

先重新确认目标代码版本和问题是否仍存在，再更新测试数量与证据；将正式正文单独保存，按当时仓库模板填写。草稿用于形成可审阅的内容，不能自动视为已满足投稿或验证条件。

选择投稿路径前先读[贡献流程阅读版](CONTRIBUTING-friendly.md)。英文技术细节和历史草稿见 [DRAFTS.md](DRAFTS.md)。
