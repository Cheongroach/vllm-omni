# LongCat-Next 下一步：先让生成过程正确，再谈速度

这份计划从当前两项局部修复出发，说明后续每一步要解决什么问题、需要什么证据。它是路线图，尚未完成的条目不能写成项目成果。技术入口和详细矩阵见 [TODO.md](TODO.md)。

## 已经完成的起点

个人 fork 已修复视觉码范围与合法 code 0 的反馈，并共享只读码表以减少重复存储。隔离 CPU 共 72 项回归通过。真实运行时、GPU/TP、生成质量和性能仍待验证。

模型适配基线为 #5299 `c90ebc1d07ba`。BF16、向量维度 3072 且两张媒体码表都已初始化时，删除一份重复表对应 882 MiB/rank；这个数字尚不能描述为完整模型真机收益。

## 最值得推进的是 CFG 配对

CFG 生图会计算有条件与无条件两路预测，再组合它们。两路各有缓存历史，却服务同一个用户请求。它们需要一起接纳、在同一生成步前进，并在正常结束、取消或出错时一起清理。

已有隔离复现显示：只调用一方时可能独立前进；两方处于不同步时仍可能被组合。下一步应先解决这种状态一致性，而不是先优化计算速度。

验收要覆盖多对请求与普通请求混合、不同提示长度、资源不足、只取消一方、正常结束和达到长度上限。等另一方时不能单独写入生成历史；结束后不能残留缓存或请求记录。方案见[CFG 阅读版](https://github.com/Cheongroach/vllm-omni/blob/longcat-next/draft-cfg-lifecycle/planning/longcat-next/drafts/cfg-lifecycle-friendly.md)。

## 后续工作按什么顺序展开

| 步骤 | 要回答的问题 | 怎样回答 |
| --- | --- | --- |
| 完整运行时验证 | 局部修复在真实加载和调度路径中是否仍成立 | 运行实际 Request、调度器、缓存管理与权重加载路径 |
| 质量对齐 | 是否保留了相同权重参考实现的生成行为 | 固定输入前缀，逐级比较分数、离散码、反馈和首个分歧，再评估自由生成媒体 |
| 请求与输出对齐 | 并发、重排、空帧和取消时，媒体是否仍属于正确请求 | 混合文字/音频/图像，检查请求编号、网格和所有输出字段 |
| 在线服务 | 目标 API 是否正确输出媒体并传递错误 | 检查尺寸、采样率、格式、超时、取消和资源背压 |
| 性能优化 | 真实时间主要花在哪里，候选修改是否改善 | 先 profiling，再比较同质量的吞吐、尾延迟与显存 |
| 多卡与 Ascend | 计算、通信、解码与精度是否支持目标平台 | 在目标硬件实际加载与执行，并对照该平台参考结果 |

RVQ 的 8 级码存在逐级依赖。优化可以把不同请求的同一级组成批次，或记录固定计算图；不能把 8 级改成互相独立的输出。

## 为什么不把所有组合一次跑完

输入大小、并发、CFG、卡数和缓存开关会交叉形成很多场景。有些组合根本不支持，有些需要稀缺资源。应先用少量确定性用例发现状态错误，再扩大并发与输入范围。

原计划建议 CFG 强度 1/3、并发 1/2/4/8、短/长上下文、单图/多图和非方形网格、文字/音频/图像混合，以及正常结束/取消/超时/缓存压力。TP=1/2/4 在资源允许且模型支持时验证。这些是候选场景，不是已通过矩阵。

更一般的资源组合问题见[组合周报](https://github.com/Cheongroach/vllm-omni/blob/longcat-next/draft-cfg-lifecycle/planning/longcat-next/drafts/weekly-2026-10-25-combinations-friendly.md)：VAE 复用已有 rank 时，不能再乘一次卡数。

## 性能结果怎样才可信

对照需要固定模型权重、框架版本、硬件、精度、并行设置、输入和采样参数，分开报告冷启动与预热后的结果。至少做三次独立运行，并记录种子和样本数；重复相同种子不能冒充多种子质量评估。

吞吐应统计每秒成功交付的有效请求，而不只计生成 token。延迟报告 P50/P95/P99，即不同百分位的请求等待时间；音频还需报告音频时长与实际生成时间的比值。失败、取消和重试都要记录。

原技术计划中的“吞吐提高至少 10%、P95 不回退超过 5%”是待确认的验收建议，不是测得收益，也不是普遍服务标准。最终阈值要在目标工作负载确定后冻结。非法码、输出串请求等正确性问题不能用吞吐补偿。

## 每一步怎样形成贡献

局部视觉修复与存储修复保持独立提交。CFG 先把职责和验收讲清楚，再做完整生命周期；在线能力、性能和平台支持各自验收。对应结果取得后，再决定适合原作者吸收还是独立投稿。

当前优先取得真实运行时与质量证据。只有设计文档、预检、任务启动或排队记录时，应直接保留“未验证”状态。
