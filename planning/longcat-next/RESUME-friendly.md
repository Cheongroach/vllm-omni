# 怎样在简历里写这项工作

这份材料把“已经做成的事情”和“计划继续做的事情”分开。完整证据清单及面试追问见 [RESUME.md](RESUME.md)。

## 当前可以写到什么程度

当前成果是个人 fork 中的两项局部修复和回归验证。可以写：

> 在个人 fork 改进 vLLM-Omni 的 LongCat-Next 适配：定位并修复视觉离散码范围与合法 code 0 的反馈错误，新增 16 项回归用例；原代码运行这些用例时 10 项失败，修复后连同既有用例共 72 项隔离 CPU 测试通过。共享深度预测网络与缓存码表的只读存储，消除重复表分配；真实 GPU、多卡和生成质量验证待完成。

较短的表述：

> 改进 LongCat-Next 多模态推理适配，修复视觉码与下一步反馈错误，补充确定性回归；共享只读码表，减少重复分配，并形成 CFG 配对调度及质量验证方案。

不能写“已合并上游”“完成三模态生产部署”或“快于 SGLang”，因为现有证据还未支持这些结果。

## 面试时怎样讲清楚工程判断

先说负责的是已有适配的正确性与存储改进，再说为什么选择这些问题：离散码既用于媒体解码，也反馈给下一步生成，因此局部错误会影响后续计算；两个只读消费者持有重复表则增加显存需求。

接着讲解决方法与取舍：每级排除额外码，按保留帧状态处理合法 code 0，共享只读存储。没有重复应用作者已经补齐的图片尺寸与请求对齐修改，也没有把有依赖的 8 级码改成完全并行输出。

最后给出对照结果与边界。16 项新增用例和 72 项总用例分别是什么、为什么使用隔离 CPU 环境、还有哪些真实运行路径未测，应该能直接解释。

## 882 MiB 是否适合放简历

这个数字可以在技术面试中解释，但必须带条件：BF16、向量维度 3072、视觉表 131072 行、音频表 19456 行，两表都在该进程初始化时，少一份表为 882 MiB/rank。

它是局部存储计算，不是当前完整模型的真机显存结果。简历篇幅不足以交代条件时，写“消除重复码表分配”更清楚；取得真实 GPU 数据后再写测得的峰值和稳态变化。

## 怎样补成更完整的项目成果

最有价值的新证据包括：对应个人提交被上游或适配作者接受；同权重参考下媒体质量保持；真实 GPU 上显存变化；并发、取消、缓存压力下 CFG 两路不会失配；同质量工作负载上的吞吐与尾延迟对照。

这些结果不必一次全部取得，但写进简历的指标必须能追溯到具体版本、硬件、并行配置、输入规模、样本数和重复运行。真实运行时验证完成但真模型未测，也应保留这个层次差别。

完成实验后的描述可按“负责范围 → 定位证据 → 实现方法 → 测量设置 → 质量和性能结果 → 接受链接”组织。未完成项继续放在路线图，不填入结果栏。
