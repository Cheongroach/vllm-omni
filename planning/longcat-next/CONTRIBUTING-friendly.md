# 怎样把个人 fork 的改进送到上游

这份材料解释当前代码为什么不能直接作为一个普通上游修复 PR，以及应该怎样组织贡献。具体 Git 命令、投稿命令与检查项保留在 [CONTRIBUTING.md](CONTRIBUTING.md)。

## 先分清三个位置

上游仓库是 `vllm-project/vllm-omni`，保存社区维护的代码。个人 fork 是 `Cheongroach/vllm-omni`，可以保存自己的分支。PR 是请求目标仓库审阅并合入某个分支的变更，推送个人 fork 不等于创建 PR，也不等于上游接受。

本地 `origin` 指个人 fork，`upstream` 指上游。worktree 是同一 Git 仓库的独立工作目录，让代码、研究和计划分支可以同时打开。

| 分支 | 用途 |
| --- | --- |
| `main` | 对齐已核对的上游代码 |
| `longcat-next/code` | 两项局部修复、测试与临时代码说明 |
| `longcat-next/docs` | 模型分析、审查、验证和讲解 |
| `longcat-next/roadmap` | 后续计划、贡献和简历材料 |
| `longcat-next/draft-cfg-lifecycle` | CFG 与组合问题的设计、周报和复现脚本 |

## 为什么当前代码不能直接向 main 投稿

代码分支基于模型适配 PR #5299 的 `c90ebc1d07ba`。调查时该模型前置还没有进入核对的上游 main，因此代码分支相对 main 的差异包含整套模型适配，而不只是两个小修复。

直接这样开 PR，会让审核者看到重复的大段模型代码，难以分清贡献范围。更适合先把两个独立修复提交交给适配作者，询问是否愿意吸收。cherry-pick 就是将指定提交应用到另一条分支，范围可以保持清楚。

另一条路径是等模型前置进入上游，再从最新 main 创建修复分支，重新应用并验证这两项改动。必须核查那时问题是否仍存在，不能盲目复制旧提交。

## issue 和 PR 分别做什么

| 材料 | 用来解决什么 | 应包含的核心信息 |
| --- | --- | --- |
| bug issue | 说明一个仍存在的行为错误 | 版本、预期与实际、最小复现、影响和未验证范围 |
| RFC issue | 讨论跨模块设计，例如 CFG 成对调度 | 要解决的用户问题、职责、替代方案和验收 |
| 修复 PR | 提交一个明确问题的实现 | 修改后的行为、对应测试和剩余限制 |

RFC 是“征求意见的设计提案”。它不代表维护者已经同意方案。本文与 [DRAFTS-friendly.md](DRAFTS-friendly.md) 只保存草稿，没有向上游发送消息或创建投稿。

## 什么会让贡献更容易审核

最重要的是让证据与差异一一对应。视觉修复报告视觉复现，存储修改报告查值和分配证据；不附带重写整个运行时，不把已被作者解决的问题继续列为缺陷。

测试先在原代码失败、再在候选版本通过，且说明是否用了运行时替身。当前 72 项通过是隔离 CPU 回归，不能写成真机或完整 CI 通过。GPU 资源不足时保留未测范围，维护者的 CI 决策不能被本地预检替代。

提交上游时重新核查当时的贡献说明、PR 模板和 AI 披露要求；将实际人类判断和 AI 协助如实说明。DCO sign-off 是贡献者对提交的声明，不是密码学签名，也不表示社区已接受。

## 如何更新分支而不丢历史

正常同步 main 使用 fetch、fast-forward merge，再推送个人 fork。fast-forward 表示分支沿已有历史向前移动；有冲突或分叉时，应先看自己的提交，不直接覆盖。

研究与计划分支保留各自基线，文档更新追加普通提交即可。旧改进分支还包含已被部分吸收的改动，不应整串应用到最新适配。同步和验证命令见[技术流程](CONTRIBUTING.md)。

这份材料沿用前序核对的版本状态，没有重新判断今天上游 #5299 是否已合并。真正投稿前需要重新确认目标版本和最新讨论。
