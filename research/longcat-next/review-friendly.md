# LongCat-Next 审查：哪些问题还值得修

本次审查希望区分“模型功能已经接入”和“运行时行为已经正确”。对象固定为模型适配 #5299 `c90ebc1d07ba`，并与此前四项本地改进比较。完整源码位置和反证保留在[技术审查原稿](review.md)。

## 审查发现了什么

图片生成依赖一组合法离散码，以及这些码给下一步计算提供的反馈。如果码范围、反馈类型或请求历史出错，接口仍可能返回结果，但结果不能据此视为正确。

前序审查确认了四个局部问题。前三项已有个人 fork 修复；第四项涉及两个内部请求的调度，尚未实现完整解决方案。

| 问题 | 为什么会影响行为 | 当前处理 |
| --- | --- | --- |
| 后续视觉级别仍可采到特殊编号 | 特殊编号不属于有效量化码，累计编号偏移后可能对应错误的反馈向量 | 已在每一级屏蔽额外类 |
| 合法编号 0 被当作“没有图像” | 该帧被保留，却给下一步反馈了文字向量 | 已按“帧是否保留”决定反馈，不再按编号是否为零判断 |
| 一张只读码表复制成两份 | 已有缓存码表被深度网络再复制一次，增加常驻存储 | 已共享只读存储，并去掉 FP32 中间转换 |
| CFG 两路缺配对或错步时仍继续 | 两路可能积累不同历史，后续组合不能只靠同步计数修复 | 已有隔离复现和设计，完整调度修改待做 |

特殊编号在技术原稿中叫 sentinel。只读共享存储在源码中叫 frozen storage；意思是两个消费者读取同一份数据，不再各保留一份复制品。

## 哪些结论需要收窄

第一项不能写成“必然数组越界”。实际量化表有额外物理行，已确定的问题是非法生成码及错误反馈含义，而不是已证明的崩溃。

第二项的编号 0 确实合法。官方量化搜索从第 0 行开始比较，并没有将返回索引整体加一；因此 0 不能充当“没有媒体”的判断条件。

第三项不是持续内存泄漏。多余复制增加常驻存储，FP32 中间转换增加初始化峰值，两者需要分别测量。在 BF16、向量维度 3072、视觉表 131072 行、音频表 19456 行且两表都已初始化时，少一份表对应 882 MiB/rank。

第四项也不是 CFG 公式本身错误。两路位于同一步时，`u + s × (c − u)` 的组合方式成立；问题是没有完整保证它们在每轮都满足该条件。容量和副本绑定分别回答“能装几条请求”和“放在哪个服务副本”，都不能代替成对调度。

## 为什么只保留两项旧提交

此前四项改进基于较早的接口。新适配已经修复部分图片尺寸传递、请求顺序和媒体输出问题，不能整串重复移植。

| 旧改进 | 这次的判断 |
| --- | --- |
| 图片尺寸和图片起始标记 | 新基线已有对应修复，不重复叠加旧 bridge |
| 视觉码范围与编号 0 | 问题仍成立，移植为最小正确性修复 |
| 请求编号、logits 行和输出载荷对齐 | 作者已吸收多项修复，需要按新接口继续验证 |
| 码表与深度网络共享存储 | 重复复制仍存在，保留独立修复 |

因此新代码分成两个提交：`b56c2a94b` 处理视觉正确性，`53785219b` 处理存储。这样每项修改可以单独复现、审核和接受。

## 测试允许说到哪里

16 项新用例在原代码上得到 10 项失败、6 项通过；修复后，加上 56 项已有用例，共 72 项通过。这里是隔离 CPU 测试，真实深度网络、TP 通信和完整运行时的部分依赖被替代。

这些结果支持局部采样、反馈和共享存储修改。它们不能证明真实图片质量、GPU 并发、完整缓存回收、Ascend 支持或端到端性能。命令与范围见[验证阅读版](VALIDATION-friendly.md)。

后续最有价值的扩展是完成 CFG 配对生命周期，再通过真实运行时与真模型对照验证。在线接口、性能优化和 NPU 适配分别需要自己的证据，不宜放入一次范围过大的修改。
